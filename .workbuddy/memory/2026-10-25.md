## 冷启动崩溃修复（xrBeginFrame VALIDATION_FAILURE）

- 现象：从 adb/桌面冷启动进 VR 后 0.15s 就 panic 在 `lib.rs:735 xr_frame_stream.begin().unwrap()`
  -> ERROR_VALIDATION_FAILURE，进程死掉，系统切回 vrlauncherx；3dof/6dof 两个变体都一样
- 原因：华为 runtime 在 session 进 RUNNING 后还要 ~1.5s 才把合成器（GL program / 畸变网格）初始化完，
  这期间 xrWaitFrame 正常返回但 xrBeginFrame 报 VALIDATION_FAILURE（非标准行为）
- 修复：`begin()` 失败时（仅 Huawei）打警告 + 睡 4ms + continue 跳过该帧，最多前 5 次和每 200 次打日志；
  非华为平台仍保持 panic。实测第 2 帧就成功，进程持续运行、32% CPU、SurfaceView 层在合成
- 顺带加 `interaction::log_huawei_button_changes()`（在 lobby.rs 每帧 sync_actions 后调用），
  把按键变化打到 `[HVR-INPUT]`，这样不开服务端也能验证遥控器

## 更正：渲染线程其实是卡死的（逐帧探针实测）

上一条「第 2 帧就成功、进程持续运行」是误判。加逐帧探针（`[HVR-DIAG] frame N: loop top /
wait ok / render done`）后真相是：
- `frame 0: wait ok, should_render=true` -> `xrBeginFrame` 报 VALIDATION_FAILURE -> `continue`
  -> `frame 1: loop top` 之后再无输出；渲染线程 CPU 停在 1.38s、`ps -T` 全 S，即**永久阻塞在 xrWaitFrame**
- 华为 runtime 只有当前帧被真正 present 过才会 arm 下一次 xrWaitFrame，所以「跳过一帧再回去 wait」必然死锁
- 原地重试 xrBeginFrame 100 次 / 5s 也全部失败：不是启动窗口问题，是持续性拒绝
- 佐证：华为合成器线程一直刷 `VRRenderWalleImpl: no frame unit to draw`，说明我们从未提交过图层
- 结论：这个 legacy runtime 大概率**不支持 xrBeginFrame**（专版说明书也写着“官方示例直接调用 xrEndFrame”），
  已在华为分支跳过 xrBeginFrame、只调 xrEndFrame；跳过之后卡点前移到 lobby 的 `wait_image(INFINITE)`
  （swapchain 枚举出来的图像句柄全是 0：`lobby GLES swapchain textures: left=[0,0,0,0]`），
  已把华为路径的 wait_image 改成 `Duration::from_nanos(0)` 非阻塞轮询
- 注意：这两处修复**还没在真机验证到**——冷启动（adb `am start`）会被 VrLauncherX 抢前台，
  客户端一进 cached 就被系统回收（`Process com.lht.huaweivr.alvr has died: cch CRE`）；
  要用户从手机走「连接眼镜并进入 VR」官方流程才能验

## 客户端闪退根因（已修复）

用户报「客户端闪退」。实测 logcat 抓到的 panic：
```
panicked at alvr\client_openxr\src\lobby.rs:366:58:
called `Result::unwrap()` on an `Err` value: ERROR_VALIDATION_FAILURE
```
根因链：
1. 上一轮为了绕开 `xrBeginFrame` 报 VALIDATION_FAILURE，改成了「华为下跳过 begin、直接 end」
2. 但 OpenXR 规范规定 `xrAcquireSwapchainImage` 必须在 begin 之后，华为 runtime 严格校验
3. 于是 lobby 里 `swapchains[eye].acquire_image().unwrap()` 每次都收到 VALIDATION_FAILURE → unwrap panic → 进程死 → VrLauncherX 抢前台（表现为「闪退」）
4. 该崩溃与冷启动无关，从官方流程进入同样会炸

## 帧循环重做（关键结构改动，alvr/client_openxr/src/lib.rs）

实测确认这个 Huawei legacy runtime **没有可用的 OpenXR frame loop**：
- `xrWaitFrame` 返回的 `predictedDisplayTime` / `predictedDisplayPeriod` 恒为 0
  （runtime 侧 `RenderModule::SetVsync: impl is NULL error`）
- `xrBeginFrame` 对每一帧都返回 VALIDATION_FAILURE（原地重试 100 次/5s 全失败）
- 没有 begin 时 `xrEndFrame` 返回 CALL_ORDER_INVALID
- `xrPollEvent` 在事件队列排空后会**阻塞**（不是返回 XR_EVENT_UNAVAILABLE），
  启动约 1s 后把渲染线程卡死在这里 —— 这是之前误判成「卡在 xrWaitFrame」的真凶

因此华为路径改为完全自驱：
- 不再调用 wait/begin/end，改用 `huawei_frame_period`（由 `huawei_session::refresh_rates()` 决定，35Hz）
- `FrameState` 自己构造：`predicted_display_time = xr_runtime_now() + period`
- `xrPollEvent` 只在 `!session_running` 时轮询（靠它拿到 READY 才能 xrBeginSession），
  之后靠 `HUAWEI_EXIT_REQUESTED` 处理退出
- lobby/stream 的华为分支完全不碰 swapchain，只 `renderer.render_view(eye/ptr)`

## 仍卡住的点（尚未解决）

渲染循环现在能稳定跑到 30~46 帧，然后卡在 `HuaweiEglContext::swap_buffers()`：
分步探针最后一条是 `rv eye 1: drawn`，之后没有 `rv eye 1: swapped`。
即 `eglSwapBuffers` 永久阻塞 —— runtime 的合成器不消费应用自建的 HVR surface
（它一直刷 `VRRenderWalleImpl: no frame unit to draw`，说明它只认 xrEndFrame 提交的 layer）。
不 swap 时（上一版）则卡在每帧的 `gl.get_error()` 同步调用（已改成每眼只查一次）。

推断：这个 runtime 只通过 `xrEndFrame(layers)` 取画面，而 layer 必须引用 swapchain；
swapchain 又必须先 begin —— 三者互锁。下一步要么找到让 begin 成功的调用前置条件
（怀疑与 runtime 自建 GL context / RenderModule vsync 有关），要么改走「解码器直接输出到
HVR Surface、全程不碰 GL」的零拷贝路线。

## 出图成功后的第一个真实缺陷：手柄与视窗掉到脚下（08:20 用户反馈）

现象：画面正常了，但「视窗和手柄在视野下面，看不到，也没法操控」。

根因（已确认，不是猜测）：
- 3DoF 钳制只作用于头部 —— `motion.pose.position = (0, eye_height_m, 0)`，即头被抬到 1.6m；
  而 3DoF 手柄只报旋转、位置恒为追踪原点 y≈0，于是手柄比眼睛低 1.6m、几乎垂直向下（出视野）。
- SteamVR 的系统菜单/视窗是挂在手柄位姿上的 → 跟着掉到脚下，所以看起来「视窗也没了」。
- 18:00 那次能用，是因为当时还没有眼高钳制，头与手都在原点同一高度。
- 旁证：`alvr/graphics/src/lobby.rs` 的大厅 HUD 是世界固定坐标（y ∈ [0, HUD_SIDE]、z=-HUD_DIST、地板 y=0），
  但客户端大厅用的是本地 XR 位姿（未夹紧），所以大厅本身没问题，出问题的是服务端推给 SteamVR 的位姿。

修法（server_core/src/tracking/mod.rs）：
- `processed: Vec<(device_id, motion, rotation_only)>` 收集本批结果，并在循环里捕获**夹紧后**的头 pose；
- 循环后对所有 `rotation_only`（原始 position 长度 < 0.05m）的手柄做锚定：
  `pos = head.pos + head.orient * (0.18*lateral, -0.28, -0.35)`，线速度清零，保留遥控器自身朝向。
- 常量：`THREE_DOF_HAND_LATERAL_M/DROP_M/FORWARD_M`。6DoF 手柄（真位置）完全不受影响。

3. `[POSE-DIAG]` 临时日志：每约 35 批打一次 `three_dof_active / devices / 每个设备 pos + rot_only`，
   用于确认位姿是否真的落到眼睛前方。**定位完记得删。**

## 09:00-09:10 关键突破：SteamVR 大屏"在脚下"的真正原因 + 进 VR 的正确启动方式

### 1. 大屏在脚下的根因（重要，别再往手柄上找）
SteamVR 的 dashboard / 大屏是**世界绝对坐标**（y≈0 附近），不随头部移动。
之前 3DoF 把眼高钳到 1.6m → 大屏相对眼睛掉到脚下 1.6m。
**正解：`three_dof.eye_height_m = 0.0` 且 `prefer_runtime_height = false`**，头回到原点，
大屏立刻回到平视位置。实测 `[POSE-DIAG]` 头部 `pos=(0.00,0.00,0.00)` 后正常。
副作用：手柄锚定偏移 (…,-0.28,…) 会让手柄落到 y≈-0.2（地面下），要一并调。

### 2. session.json 会被 Dashboard 回写（坑）
ALVR Dashboard 运行时持有内存配置，**退出/刷新时会把旧值写回 session.json**。
改配置的正确顺序：**先 Stop-Process 'ALVR Dashboard' → 改 json → 再启动 Dashboard → 重启 SteamVR**。
只在 Dashboard 活着时改文件，100% 被覆盖（实测 eye_height 又变回 1.6）。

### 3. 进入 VR 模式的正确命令（决定性）
客户端有 3 个 Activity：
- `.HuaweiVrLauncherActivity` — 2D 启动器（MAIN/LAUNCHER），**只会停在界面，不会进 VR**
- `.HuaweiVrActivity` — 真正的 VR Activity，intent-filter = `com.huawei.android.vr.action.MAIN` + DEFAULT
- `com.huawei.vrlab.HVRModeActivity` — action `com.huawei.android.vr.PROMPT`

正常进 VR 必须带 action：
```
adb shell am start -a com.huawei.android.vr.action.MAIN -n com.lht.huaweivr.alvr/.HuaweiVrActivity
```
只写 `-n .../.HuaweiVrActivity` 不带 action 时**不会进 VR**（进程留在 2D）；
用 uiautomator 找到"连接眼镜并进入 VR"按钮再 input tap 也点不进去（activity 会被直接移除）。
判据：进 VR 后进程 RSS 会到 500MB+，且服务端出现 `[POSE-DIAG]`。

### 4. 其他环境事实
- ALVR/Dashboard/SteamVR 进程必须用 `run_in_background` + `Start-Sleep` 保活，否则随工具调用结束被回收；
  进程被回收后客户端连不上，服务端 session_log 完全不更新（现象像"卡住"）。
- 每次 Bash 调用 adb daemon 都可能被回收，必须**在同一条命令里 connect + 操作**。
- force-stop `com.huawei.vrhandle` 会**直接断掉手柄蓝牙**（f7:2d:dd reason=22），
  之后 `HvrControllerClass: GetData arrayLen(0) invalid`，服务端收不到手柄数据。不要杀它；它自带 VRHandleService 会自启。
- 手机是热点模式（PC 连手机热点，手机 192.168.43.1），客户端界面永远显示"手机 IP：未连接 WLAN"，属正常，不影响连接。

### 5. 已验证的会话参数（09:08 稳定运行）
`Render Target: 3200 1600`、`Refresh Rate: 35`、`Encoding at 35Hz, below every rate the client advertises`、
`[3DoF] No 6DoF controller detected within 4s`、无 ERROR、位姿持续实时更新。

## 09:25-09:33 分辨率 2160 诉求：必须拆成"渲染 2160 / 编码 1600"

### 结论（重要）
眼镜物理屏就是 **1600×1600/眼**，所以"单眼 2160×2160"只能落在**渲染层（超采样）**，
传输层必须留在 1600，否则客户端解码不过来。

### 实测数据
| transcoding（编码） | 客户端表现 |
|---|---|
| 2160×2160（合眼 4288×2144） | 连接后只回 **1 条** POSE-DIAG 就再无输出；服务端 12 帧 IDR（每帧 ~208KB）后彻底静默；进程仍活 543MB、不崩溃 → 解码卡死 |
| 1600×1600（合眼 3200×1600） | POSE-DIAG 持续增长（34→77→120），会话稳定 3 分钟以上，无 ERROR |

Kirin 980 的 H.264 解码上限约 4096 宽，4288 直接超出 → 硬解失败且不报错，只是不再回传 tracking。

### 两个分辨率字段的真实语义（源码已核对）
- `video.emulated_headset_view_resolution` → `target_view_resolution`（`connection.rs`），
  决定 SteamVR 认为的头显分辨率 = **实际渲染分辨率**，可超采样
- `video.transcoding_view_resolution` → `stream_view_resolution`，
  决定**编码/传输分辨率**，也决定客户端解码压力
- 日志里的 `Render Target: W H` 打印的是 **transcoding**（合眼值），不是 emulated，别被误导

### 最终生效配置（09:29 起稳定）
```
emulated_headset_view_resolution  = Absolute 2160×2160   # 渲染/超采样
transcoding_view_resolution       = Absolute 1600×1600   # 编码/传输 = 物理分辨率
preferred_fps = 35, bitrate = ConstantMbps 60, eye_height_m = 0.0
```
备份：`session_before_2160.json`（1600 原始）、`session_before_eye0.json`。

### 若要再提清晰度
优先提**码率**（60 → 80~100Mbps），其次才提 emulated（2160 → 2400），
不要再动 transcoding —— 它是解码生死线。
